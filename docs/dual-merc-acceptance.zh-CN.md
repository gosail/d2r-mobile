# 双佣兵离线功能：可验收条件与实验限制

> 本文件描述目标行为与尚未完成的验收条件。**当前 PR #5 不代表完整双佣兵功能，未通过实机验收；不可用于珍贵角色档。**

## 目标交互

| 当前佣兵 | NPC 候选 | 期望动作 | 是否弹出选择旧佣兵 |
|---|---|---|---|
| 0 名 | 任意有效幕（I/II/III/V） | 直接雇佣，成为位置 1 | 否 |
| 1 名（第一幕） | 第二幕 | 增加第二名，两人同时存活、跟随和战斗 | 否 |
| 1 名（第二幕） | 第二幕，任意难度 | 正常确认替换第二幕佣兵 | 否 |
| 2 名（第一幕+第二幕） | 第三幕 | 先选择替换第一幕或第二幕，再确认 | **是** |
| 2 名（第一幕+第二幕） | 第二幕，任意难度 | 只能替换已有第二幕；原第一幕必须保留 | 否 |
| 2 名（第一幕+第二幕） | 第一幕，任意难度 | 只能替换已有第一幕；原第二幕必须保留 | 否 |
| 2 名且其中一名死亡 | 任意候选 | 死亡佣兵仍占用幕名额和位置 | 根据上面两条规则 |
| 2 名且一个来自第五幕 | 第五幕，任意难度 | 同幕只替换原第五幕；不可出现两个第五幕佣兵 | 否 |

第四幕没有可招募的独立佣兵类型，NPC 复活入口不能算新招募幕。

## 每次事务必须同时通过的验收

1. **雇佣业务**：扣金币或完成确认前就确定位置；取消任何选择必须无副作用；替换失败必须回滚。
2. **服务器队伍**：宠物类型 7 的链表中活跃数量不超过 2，来源幕不得重复；原来的第一名绝不可被新候选无意解除关联或销毁。
3. **客户端显示**：玩家和两个佣兵共同移动、攻击、跨区、回城、切换地图、重进游戏；死亡或复活状态和角色一致。
4. **装备管理**：两套独立面板或一个面板的显式佣兵选择；每件物品只有一个有效持有者。佩戴、卸下、拖动、复制/售卖防护，以及带孔装备与符文必须对两个佣兵一致。
5. **读档**：每名佣兵身份、等级、经验、名字、技能、装备、死亡状态均可完整恢复；原版 .d2s 所属佣兵位置必须和 .swmerc 标记一致。
6. **原子性**：角色 .d2s、扩展 .swmerc 与任何相关仓库旁路文件一次性提交；出现损坏或旧版本要拒绝加载扩展状态，不能复制物品或清空合法角色资料。
7. **兼容性**：线上模式和普通版完全不启用这套修改；不得修改 Bundle ID；升级前有可独立恢复的存档备份。

## 目前已实现（源代码）

- 纯 C 位置策略以及不同难度下同幕唯一性（`dm_dualmerc_policy.h`）
- `SWM2` v3 两名佣兵的身份及各自最多十件装备位流的**未接线**编解码器（`dm_dualmerc_state.h`）
- 具备临时文件、写盘刷盘、原子改名及损坏拒绝的 `.swmerc` **未接线**磁盘模块（`dm_dualmerc_disk.h`）
- 原生 0x687648 查询 hook：仅实验包、旧佣兵及新候选都无装备、来源幕不同，尝试保留第一名；已满两名及装备状态未验证时，阻止原版雇佣命令自动替换（`diag.c`）
- 仅当原生绑定后服务器链表同时包含旧/新两个准确的佣兵 ID 才显示试验提示；仍不声称客户端 UI 和存档已完成

## 目前未实现

**双位置替换的 UI 和一次性选择事务已接入实验性 C2S 路径，但仍未经编译和实机验证。** 尚未实现两套可切换装备面板、完整佣兵第二位置的原生保存和载入/重建、经验死亡与复活并行、地图切换和退出重进的全场景验证。原版 NPC “新雇佣将替换旧佣兵”对话也尚未做条件适配。

## 一次性实验操作（仅专用测试 IPA）

1. 用无价值、独立备份的离线角色进入游戏；不要给佣兵任何装备。
2. 雇佣一个第一幕佣兵，确认能正常跟随和战斗。
3. 去第二幕，雇佣一个不带装备的第二幕佣兵。确认两人同时出现在实际场景，不能仅凭数据表上限或 NPC 文案判断。
4. 检查游戏提示是否实际检测到宠物节点数量 = 2。如果没有出现，保留控制台日志：`DM_DUAL_MERC_TRIAL`、`DM_DUAL_MERC_NATIVE`、`DM_DUAL_MERC_PROBE`。
5. **不要在这个尚未具备第二佣兵读档的实验版中给第二名佣兵装备，也不要将成功进入双佣兵状态当成存档可恢复的证明。**

当前离线实验 IPA 使用 `DM_DUAL_MERC_KEEP_FIRST=0` 可关闭临时保留；普通版不存在 0x94 游戏代码 hook，不受这个实验逻辑影响。

## 2026-11-18 回归保护

存档状态机对需要替换的旧佣兵，如仍持有任何装备，即使候选位置正确也拒绝直接覆盖旧记录；必须先在原生游戏界面卸下并由引擎完成装备移交。单元测试还检查装备身份重复、损坏/校验失败、同幕跨难度限制，以及不同难度的死亡佣兵仍占位置。

原生保留实验已修复 UNIT 指针与宠物链表 NODE 指针误比的问题。新版在 `0x6c1b00` 返回之后还必须检查两名准确的原生 ID；验证不到两名则不显示成功提示。**此时不具备通过后恢复旧佣兵的能力**，因此不能在重要存档中进行实验。

## 2026-11-19：存档恢复安全路径与装备独立性

- 原生装备命令 `0x5b` 包含 **物品单位ID、目标佣兵单位ID、被替换物品ID、身体部位、背包格**，无需推断当前技能/装备面板指向哪名佣兵。增加 `dm_dualmerc_equip.h` 对精确包长度与对象 ID 的解析和验证。
- 二佣兵并存时，在持久化与装备 UI 完成之前，实验入口主动阻断原生 `0x51` 和 `0x5b` 装备修改，避免给第二人穿装备后退出游戏丢失或使客户端显示错位；普通只有一名佣兵的游戏不受此保护影响。
- 扩展存档升级为 **SWM2 v3**：在两个独立角色槽和各自物品位流之外，记录原版 `.d2s` 的 32 位校验和、控制种子（而不是运行期单位ID）。原版雇佣动作使旧存档绑定失效，不准带旧绑定写盘。
- `dm_dualmerc_d2s.h` 以只读方式验证旧版 D2R 文件版本 97/98/99、文件头、整档校验和和原版佣兵身份。拒绝未验证的 105 版布局、身份/经验/种子/文件校验不匹配、坏文件。
- `dm_dualmerc_disk_save_verified` 和 `dm_dualmerc_disk_load_verified` 在同一个角色工作目录中，要求原版 `.d2s` 与 `.swmerc` **身份/校验和匹配** 才允许保存或恢复扩展结构。应在现有存档事务锁与同一次 commit 里使用，目前还没有真正绑定到游戏引擎。
- `dm_dualmerc_restore_plan` 在通过原版身份验证之后，**只返回非原版位置**为扩展恢复目标，绝不重复创建原版 .d2s 已经保存的佣兵。重复物品ID、同幕重复、错误版本或错误种子均拒绝。
- 当前仍欠缺**真实引擎序列化源**、二佣兵原生创建和装备重建、独立复活、原生事务失败回滚；这些必须通过 iPad 真机和跨局存盘测试才能放开二佣兵装备写入。当前状态不得用正式角色和物品做测试。

这些新文件配有合成存档和回归测试；仓库 Actions 在 preflight 没有执行任何步骤即失败，所以**不能宣称已通过本轮 CI 或 iPad 原生编译**。


## 2026-11-19：存档残留装备与 iPad 选择框竞态防护

- `dm_dualmerc_state_valid` 现在要求每个佣兵 `gear_count` 之外的物品记录（部位、持久物品 ID、长度和位流）全部清零。即使 `gear_count=0`，只要内存里留有旧装备位流，就拒绝状态编码与替换，避免误认为装备已安全移交后覆盖唯一的物品记录。单测覆盖此情况。
- iPad 替换选择器给当前 UIKit 弹窗另存 nonce：旧弹窗的延迟取消闭包只允许关闭相同 nonce 的弹窗，不能把下一次 NPC 的新弹窗一起关闭。轮询和取消使用比较交换，不能把新请求的 nonce 无条件清零。
- CI 加入 `test_dualmerc_chooser_source.py` 检查上述控制流；**源码检查不能替代 Xcode 编译和真机取消/重选压力测试**。
- 上述修改没有连通第二佣兵的真实装备界面、原生存档恢复和失败回滚，不应解除双佣兵状态下原有的 `0x51/0x5b` 穿戴限制。PR 继续 Draft，普通版、正式角色以及 Bundle ID 均未修改。

## 2026-11-19：死亡佣兵在实验性原生雇佣前的保护

- 当玩家只有一名**已死亡**佣兵，又尝试从不同幕新增第二名时，实验原生 `keep-first` 不具备保留死亡单位的验证路径；现在在 C2S 原生扣费前拒绝，避免旧原生单佣兵流程误替换掉死亡佣兵。
- 当队伍已满两名，**同幕直接替换的目标已死亡**时，在进入原生处理前拒绝；新幕两选一的场景若玩家选择已死亡佣兵，也不重新投递挂起的雇佣包。
- 游戏会显示明确提示：`死亡佣兵的双佣兵雇佣/替换尚未验证，本次已取消`。规则仍将死亡佣兵计入现有名额，未放宽到两名同幕佣兵。
- 这是一项保守的实验保护限制，**不是完成了死亡佣兵替换或独立复活**；若想开放该交互，需要先在原生游戏里证实删除/复活和费用回滚事务。

## 2026-11-19：原生 Hireling 数据表校验与替换异常失败即停

- 新增 `dm_dualmerc_hire_rows.h` 及 `test_dualmerc_hire_rows.c`。离线测试构建在**第二次及之后**雇佣时读取游戏当前已加载的 Hireling 表：表入口 `main+0x2d64a18`、记录指针 `T+0x558`、数量 `T+0x560`、跨度 `0x150` 已在项目 `dm_rift.c` 中使用。按界限最多读取512行，内存不可读、冲突或候选不匹配就拒绝原生雇佣。
- 候选字段语义目前**没有通过 Switch 3.3 原生包/调用栈确认**。经典 1.13c 协议研究表明 `0x36` 的第二个 u32 可能是**佣兵名字索引**，而 `Hireling.txt` 同时拥有独立的 `Id` 类型号。验证器分别按 `Id` 和已解析的名字编号范围检查，要求恰好一种解释匹配；两种同时匹配或跨幕/跨 NPC/跨难度冲突时拒绝。名字索引范围的 `+0x114/+0x116` 等字段来自 1.14d Hireling 记录描述，**对 Switch 3.3 仍需验证**。
- 首次雇佣仍遵循**完全原版**原生路径，只追加只读匹配诊断，即使识别失败也不阻止首雇佣。记录会标明“名字索引”或“类型编号”，有助于从玩家合法游戏包实测判断当前版本字段。
- 不允许将只读表项匹配当作完成了 native `0x36` 包的语义确认；真正授权仍需该版本原生实测。
- 完成两名佣兵时的**替换后**状态校验：目标 ID 必须消失、另一原有 ID 必须保留、来源幕匹配的新单位必须出现、原生选择 Hook 必须被触发。若任何一项不满足，实验版 `die` 终止进程，以免继续保存已知异常的单位列表。这不保证游戏原生金币或装备的回滚，也不证明另一名可跨区或退出重进。
- 新校验与状态检查已写入静态/纯 C 单测及 PR CI 工作流；GitHub 仓库还没有本轮成功运行的完整 CI 或可用新 IPA，原生布局及保存/恢复仍未接通。**只允许可丢弃的离线角色验证，PR 保持 Draft。**

## 2026-11-19：iPad 选择框原子通道与存档绑定辅助流程
