# 离线双佣兵原生雇佣链：Switch 3.3 静态定位（2026-11-17）

> 本文记录可复现的只读函数定位，**未实现双佣兵**，不得直接从这些地址写入/跳过指令，也不得在贵重角色上测试。

## 版本与来源

- 游戏模块：原始 Switch 3.3 `main`，Build ID `db0507f36b84200ac05f75d76ed5026f`；由玩家本人 Prepared iOS 包的 `Guest.framework` 结构复原原始 RVA 对应的指令空间，只读。
- 分析执行于私有 `gosail/d2` Actions，检查记录 #43914829700、#43915088310、#43915266843、#43915476973、#43915714480、#43916067631。验证成功，原始游戏文件字节未进入 PR。
- 表入口 `main+0x20a4190`，命令表的已重定位 `0x36` 指向 `main+0x6dad90`，`0x38` 指向 `main+0x6db140`，`0x62` 指向 `main+0x6e5880`。候选操作码的真实游戏含义需与真机包流交叉验证。

## 雇佣函数链：已确认的控制流

1. `0x6dad90`，函数长度 `0x90`：要求 C2S 包长 17 字节；读取四个 32 位数据；`BL 0x7f2320` 获取范围内交互单位；最终 `B 0x7ef690` 转入下游处理。`0x7f2320` 还包括距离检查；这不是可直接跳过的“替换”入口。
2. `0x7ef690`，长度 `0x9e0`：检查玩家状态与 NPC、雇佣相关表；在 `0x7ef778` 调 `0x6c3130(game, player, 7, 1)` 寻找现有宠物类型7单位，将现有单位 ID 与请求参数比较，若不符可能走拒绝分支；还检查所需金币、等级、雇佣候选、玩家当前区域和客户端通知。
3. `0x7ef690` 在 `0x7efd04` 调 `0x695fd0`，必要时在 `0x7efd28` 调 `0x695eb0`（内部调用 `0x695fd0`）；在 `0x7efd3c` 调 `0x7eab30`（多个属性值处理）；在 `0x7efd64` 调 `0x6875a0`；在 `0x7efe70` 调 `0x7e9680`。后者的确切契约尚未逐项验证。
4. `0x6875a0`，长度 `0x650`：在 `0x687648` 再次以类型7查现有佣兵；已有单位时会进入原生处理分支，其内部调用 `0x6c0c30`（`0x6877f0`），再调用 `0x7cb6d0`（`0x68786c`，其下游调用包括物品从容器脱离 `0x55e430`）。在 `0x687940` 还调用 `0x6c1b00`；这几个调用的实际删除、装备脱离、单位创建/所有权变更语义必须通过函数具体入参和状态对照再确认。
5. `0x6875a0` 在 `0x687af8` 与 `0x687b04` 还调用 `0x687bf0`、`0x6883e0`（都涉及类型7单位及属性处理），不能忽略创建后初始化的后续路径。

## 禁止的捷径

- 不能仅将 `pettype.hireable.basemax` 改为2：原生单佣兵流程照样处理旧单位。
- 不能只改 NPC 雇佣确认框，服务端仍旧按单佣兵进行处理。
- 不能直接 NOP `0x6877f0`、`0x68786c`、`0x687940` 或改变候选函数返回值；必须确认对宠物表、背包、死亡标识、角色存档引用的完整影响。
- 不得直接用运行时 unit ID 作为存档长期身份；同一幕（不同难度）永远只有一个名额；已死亡佣兵仍占名额。
- 不要将任何游戏原版代码、未授权 ROM 或解出的资源写入公共仓库。

## 下一步所需的验证

1. 以无装备测试角色执行第一幕→第二幕雇佣，观察 `0x36` 包与服务端/客户端快照，证明指令链与真人操作对应（目前只有静态分析）。
2. 只读追踪 `0x6c0c30`、`0x7cb6d0` 和 `0x6c1b00` 的进入/返回状态；记录旧宠物列表、装备容器指针、金币、候选记录 ID 在雇佣前后的变化。
3. 确认原生两只单位共存不会同时占用单一玩家的佣兵控制字段或反复自行纠正为一只；测试地图切换、死亡和客户端显示。
4. 只有保留原佣兵所有权、装备位流和费用事务的安全路径验证后，才接入按幕选择替换、两套装备 UI、独立复活和版本化 `.swmerc` 侧文件（与角色档同一次提交，避免复制和丢失）。

## 只读装备链状态追踪（2026-11-17 新增）

实验版 `DM_DUAL_MERC_PROBE` 在服务端观察每个宠物类型 7 单位时额外尝试读取 `unit+0x90` 的 inventory 指针：必须匹配已在本项目玩家单位上使用的签名 `0x01020304`，再沿原生物品链 `inventory+0x10 → [item+0x10]+0xb0` 最多扫描 64 件。不调用原生物品创建或释放函数，不改变装备内容。其在佣兵单位上的实际覆盖率仍需真机验证。

每条快照末尾新增 `inv<件数>/<状态>:h<十六进制指纹>`。状态 0=无 inventory 指针、1=完整可读、2=不可读/签名异常、3=超过64件已截断。指纹是运行时物品 ID 的顺序无关轻量摘要，允许同局前后对比，不适合跨角色档或证明所有权。宠物表中原佣兵 ID 消失时单独报告最后一次装备快照；**佣兵消失不等于其装备丢失**，状态0/2/3不能解读为空装备。

该项检查对完整正式游戏仍然默认关闭。建议先用空佣兵验证，再使用新建测试角色和无价值装备核对物品归属；不要在未知时直接执行释放、复制或存盘侧文件。

## 从真机日志归纳可复核状态（只读）

新脚本 `dm/verify/merc_probe_report.py` 输入实际导出的游戏日志，自动将候选 `0x36` 事件与其同拍原生处理之前的快照及后续 100 拍快照关联，对比旧、新佣兵 ID，标注 `replacement_in_server_list`、`two_units_in_server_list_only`、`two_units_in_both_lists` 或 `insufficient_snapshots`。以该记录区分*列表短暂共存*和*持久并肩作战*；后者必须由玩家实机测试确认。

    python3 dm/verify/merc_probe_report.py /path/to/diagnostic.log --json /tmp/merc-observation.json

如果没有候选命令，输出 `0 requests`，表示暂缺真实对应操作码的证据，**不代表客户端没有发送雇佣请求**。装备字段来自有限的只读指针扫描，不能据指纹相等认定物品未丢，也不能跨存档比较。

## 函数边界防漂移检查

新增 `dm/verify/hire_chain_contract.py`：对已验证 Switch 3.3 Prepared 游戏映像内 8 个关键 AArch64 `B/BL` 指令的位置、类型、目标 RVA 进行只读校验；游戏更新或代码改写导致调用关系变化时明确失败。已验证的具体关系包括命令入口 `0x6dadcc→0x7f2320`、下游 `0x6dadf8→0x7ef690`、旧宠物处理 `0x6877f0→0x6c0c30`、`0x68786c→0x7cb6d0`、`0x687940→0x6c1b00`。**这仅证明分支关系，没有证明任何调用可安全跳过。**

## 原生雇佣三个调用点的精确透传（实验版，新增）

仅 `DM_OFFLINE_DUAL_MERC_TEST=1` 的离线测试构建，会在 `patch_nso.py` 中以严格原始指令校验把 3 个 `BL` 位置替换为宿主 `SVC`：

- `0x6877f0 BL 0x6c0c30 → SVC 0x91`
- `0x68786c BL 0x7cb6d0 → SVC 0x92`
- `0x687940 BL 0x6c1b00 → SVC 0x93`

`dm/host/diag.c` 中的 `dm_dualmerc_native_call` 把原始 `x0..x5` 参数逐一传给对应原生函数，**无条件执行原版调用，不跳过销毁、不改变物品**；对 `DM_DUAL_MERC_PROBE=1` 的构建额外打印调用点前后两侧宠物列表快照与候选新旧单位的类号。只读函数及原始字节/编码由 `dm/tools/dualmerc_native_cuts.py` 生成和验证。普通版本完全不引入这三处剪口。

这一阶段的验证目标是明确 `0x6c0c30`、`0x7cb6d0`、`0x6c1b00` 分别在哪一步使旧单位从宠物表消失、使旧单位失效、让新单位进入列表。实验版仍沿用原版单佣兵雇佣逻辑，**暂不支持第二佣兵持久化**。在这组实机调用记录证据出现以前，不得启用“跳过旧佣兵销毁”的正式游戏功能。

## 第二佣兵原生保留试验（2026-11-17）

新增可选 `SVC 0x94`，接管原生 `main+0x687648 BL main+0x6c3130` 查询；原字节严格校验为 `baee0094`。宿主仍先调用原始查询。仅在显式环境变量 `DM_DUAL_MERC_KEEP_FIRST=1`、**服务器当前恰好一名佣兵**、候选来源幕不同且合法、旧佣兵和候选装备扫描完整且确认 0 件、旧单位存活、返回的链表节点与玩家宠物链一致时，才将**这一次查询**返回值改为 null；原生下一条 `0x68764c CBZ` 于是进入原本的「无需拆旧佣兵」新佣兵登记流程。这一实验**没有直接抹掉/删除/转移任何旧单位或物品**。

第二佣兵在服务器宠物链真实加入成功与否、客户端是否显示两名、地图传送和重启读档，均**没有实机验证**，不得声明已经完成。仅在带有 `SVC 0x94` 的离线实验 IPA 默认启用该试验，可用 `DM_DUAL_MERC_KEEP_FIRST=0` 关闭；仅能在无价值、无装备测试角色中使用；如果服务器已有两名，收包入口先拦住原版 `0x36` 雇佣请求并提示替换选择界面尚未完成，防止自动误删。旧 NPC 的原版文字仍提示替换，尚未改动。

增加纯 C 文件 `dm_dualmerc_trial.h`，测试同幕、满员、死亡、装备异常均不进入保留试验。扩展 `dm_dualmerc_state.h`（`SWM2` v3）及 `dm_dualmerc_disk.h` 为两个独立佣兵身份、十个物品位流、原版 `.d2s` 归属槽标记、写盘原子性和校验和的**尚未接入的存档组件**。原版 `.d2s` 的佣兵交接、第二佣兵加载/重建、两套装备面板、独立复活与双佣兵继承的实际游戏逻辑仍未完成；不能在正式玩家角色上启用。 

### 实验 IPA 的保护开关

只有包含 `SVC 0x94` 的专用离线试验 IPA 才会自动尝试保留首佣兵；普通版本没有这个门，行为不变。可使用 `DM_DUAL_MERC_KEEP_FIRST=0` 关闭试验。第二名佣兵不保证存档恢复，必须使用可丢弃的空装备测试角色。若已存在一名装备非空/装备状态不可验证的佣兵，则在投递 `0x36` 雇佣包前拒绝；若已有两名，也拒绝原版不带选择的替换包，避免装备丢失。 

## Native UNIT 与宠物链表节点的指针区别（2026-11-18 修复）

此前实验代码把 `main+0x6c3130` 返回的原生 **UNIT 指针**当作玩家宠物类型7链表上的 **pet node 指针**，导致 `first != node` 恒真，从未触发保留首佣兵分支。根据真实 Switch 3.3 反汇编，原生查询通过节点 `node+4` 获取 ID，再查询 `G+0x2630` 单位哈希桶，最终返回 **UNIT 地址**。现已修改为：旧单位 `unit+8` 的 ID 与宠物节点 `node+4` 的 ID 严格比较，并复查单位类型、动画模式与服务器哈希表；旧单位死亡/不可读及候选 ID 异常时不进入实验分支。

还修复了四个跳转点扩展后的合成 Mach-O 单测：第四处原生入口 `0x687648` 不得再属于「未变区域」；门号插入顺序 `0x94,0x91,0x92,0x93` 必须逐项验证，而不能假设从 `0x91` 线性递增。

在实际 `0x6c1b00` 绑定返回之后再次遍历服务端宠物链并核对**旧佣兵 ID 和新佣兵 ID 同时存在**；两个链表节点的数量单独达到2不再足以触发“已验证双人”提示。这是**服务器瞬时验证**，还不能证明客户端跟随、保存/读取、装备隔离。任何失败只记录诊断，不会声称功能已完成。

原生外部服务端逻辑 `0x6c1b00` 在函数体内另有 `0x6c0c30` 的调用；由于尚未取得本次真机雇佣日志，不能预设这些分支对旧佣兵安全。必须继续使用空装备、可丢弃存档并通过真实 iPad 实测，所有用户正式存档保持禁用。

## 保存文件跨版本和双佣兵装备保护（2026-11-19）

原版 D2R 97–99 的 `.d2s` 佣兵字段采用未迁移的头部位置：177 死亡标志、179 控制种子、183 名字索引、185 Hireling 行、187 经验，文件包含总长度及滚动校验值。105 版已改版，需要显式拒绝，绝不盲读相同偏移。为避免只看行号/名字仍误把其他存档当同一佣兵，`SWM2 v3` 现额外记录原版存档的完整校验值和佣兵控制种子；两份文件必须同时匹配才允许读写扩展状态。原版佣兵位置不重复重建，仅恢复另一槽的计划有独立测试。

原本的玩家背包直穿佣兵命令 `0x5b` 在 25 字节原生包中明确携带目标佣兵 ID，这使未来分开装备不必设计私有物品转移算法；但当前第二佣兵装备落盘及恢复未接通，实验版已有两个佣兵时，客户端发出的 `0x51` 和 `0x5b` 新装备命令会被阻止。此保护可能让实验版无法给两名佣兵换装，但可避免尚未支持的装备状态写入不完整存档。
