# 离线双佣兵原生雇佣链：Switch 3.3 静态定位（2026-11-17）

> 本文记录可复现的只读函数定位，**未实现双佣兵**，不得直接从这些地址写入/跳过指令，也不得在贵重角色上测试。

## 版本与来源

- 游戏模块：原始 Switch 3.3 `main`，Build ID `db0507f36b84200ac05f75d76ed5026f`；由玩家本人 Prepared iOS 包的 `Guest.framework` 结构复原原始 RVA 对应的指令空间，只读。
- 分析执行于私有 `gosail/d2` Actions，检查记录 #43914829700、#43915088310、#43915266843、#43915476973、#43915714480、#43916067631。验证成功，原始游戏文件字节未进入 PR。
- 表入口 `main+0x20a4190`，命令表的已重定位 `0x36` 指向 `main+0x6dad90`，`0x38` 指向 `main+0x6db140`，`0x62` 指向 `main+0x6e5880`。候选操作码的真实游戏含义需与真机包流交叉验证。

## 雇佣函数链：已确认的控制流

1. `0x6dad90`，函数长度 `0x90`：要求 C2S 包长 17 字节；读取四个 32 位数据；`BL 0x7f2320` 获取范围内交互单位；最终 `B 0x7ef690` 转入下游处理。`0x7f2320` 还包括距离检查；这不是可直接跳过的“替换”入口。
2. `0x7ef690`，长度 `0x9e0`：检查玩家状态与 NPC、雇佣相关表；在 `0x7ef778` 调 `0x6c3130(game, player, 7, 1)` 寻找现有宠物类型7单位，将现有单位 ID 与请求参数比较，若不符可能走拒绝分支；还检查所需金币、等级、雇佣候选、玩家当前区域和客户端通知。
3. `0x7ef690` 在 `0x7efd04` 调 `0x695fd0`，必要时在 `0x7efd28` 调 `0x695eb0`（内部调用 `0x695fd0`）；在 `0x7efd3c` 调 `0x7eab30`（多个属性值处理）；在 `0x7efd64` 调 `0x6875a0`；在 `0x7efe70` 调 `0x7e9680`。后者的确切契约尚未逐项验证。
4. `0x6875a0`，长度 `0x650`：在 `0x687648` 再次以类型7查现有佣兵；已有单位时会进入原生处理分支，其内部调用 `0x6c0c30`（`0x6877f0`），再调用 `0x7cb6d0`（`0x68786c`，其下游调用包括物品从容器脱离 `0x55e430`）。在 `0x687940` 还调用 `0x6c1b00`；这几个调用的实际删除、装备脱离、单位创建/所有权变更语义必须通过函数具体入参和状态对照再确认。
5. `0x6875a0` 在 `0x687af8` 与 `0x687b04` 还调用 `0x687bf0`、`0x6883e0`（都涉及类型7单位及属性处理），不能忽略创建后初始化的后续路径。

## 禁止的捷径

- 不能仅将 `pettype.hireable.basemax` 改为2：原生单佣兵流程照样处理旧单位。
- 不能只改 NPC 雇佣确认框，服务端仍旧按单佣兵进行处理。
- 不能直接 NOP `0x6877f0`、`0x68786c`、`0x687940` 或改变候选函数返回值；必须确认对宠物表、背包、死亡标识、角色存档引用的完整影响。
- 不得直接用运行时 unit ID 作为存档长期身份；同一幕（不同难度）永远只有一个名额；已死亡佣兵仍占名额。
- 不要将任何游戏原版代码、未授权 ROM 或解出的资源写入公共仓库。

## 下一步所需的验证

1. 以无装备测试角色执行第一幕→第二幕雇佣，观察 `0x36` 包与服务端/客户端快照，证明指令链与真人操作对应（目前只有静态分析）。
2. 只读追踪 `0x6c0c30`、`0x7cb6d0` 和 `0x6c1b00` 的进入/返回状态；记录旧宠物列表、装备容器指针、金币、候选记录 ID 在雇佣前后的变化。

4. 只有保留原佣兵所有权、装备位流和费用事务的安全路径验证后，才接入按幕选择替换、两套装备 UI、独立复活和版本化 `.swmerc` 侧文件（与角色档同一次提交，避免复制和丢失）。

## 只读装备链状态追踪（2026-11-17 新增）

实验版 `DM_DUAL_MERC_PROBE` 在服务端观察每个宠物类型 7 单位时额外尝试读取 `unit+0x90` 的 inventory 指针：必须匹配已在本项目玩家单位上使用的签名 `0x01020304`，再沿原生物品链 `inventory+0x10 → [item+0x10]+0xb0` 最多扫描 64 件。不调用原生物品创建或释放函数，不改变装备内容。其在佣兵单位上的实际覆盖率仍需真机验证。

每条快照末尾新增 `inv<件数>/<状态>:h<十六进制指纹>`。状态 0=无 inventory 指针、1=完整可读、2=不可读/签名异常、3=超过64件已截断。指纹是运行时物品 ID 的顺序无关轻量摘要，允许同局前后对比，不适合跨角色档或证明所有权。宠物表中原佣兵 ID 消失时单独报告最后一次装备快照；**佣兵消失不等于其装备丢失**，状态0/2/3不能解读为空装备。

该项检查对完整正式游戏仍然默认关闭。建议先用空佣兵验证，再使用新建测试角色和无价值装备核对物品归属；不要在未知时直接执行释放、复制或存盘侧文件。

## 从真机日志归纳可复核状态（只读）

新脚本 `dm/verify/merc_probe_report.py` 输入实际导出的游戏日志，自动将候选 `0x36` 事件与其同拍原生处理之前的快照及后续 100 拍快照关联，对比旧、新佣兵 ID，标注 `replacement_in_server_list`、`two_units_in_server_list_only`、`two_units_in_both_lists` 或 `insufficient_snapshots`。以该记录区分*列表短暂共存*和*持久并肩作战*；后者必须由玩家实机测试确认。

    python3 dm/verify/merc_probe_report.py /path/to/diagnostic.log --json /tmp/merc-observation.json

如果没有候选命令，输出 `0 requests`，表示暂缺真实对应操作码的证据，**不代表客户端没有发送雇佣请求**。装备字段来自有限的只读指针扫描，不能据指纹相等认定物品未丢，也不能跨存档比较。
