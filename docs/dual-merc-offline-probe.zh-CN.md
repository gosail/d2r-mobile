# 离线双佣兵——第一阶段验证

**当前仅测试佣兵类别上限以及只读观测，并没有实现完整双佣兵。** 雇佣、替换、装备、升级、复活、存档原生逻辑尚未改写。

## 实现边界

- 默认关闭：DM_OFFLINE_DUAL_MERC_TEST=0。
- 实验构建：DM_OFFLINE_DUAL_MERC_TEST=1；必须安装固定的 D2R 3.3 Excel→BIN 编译器，环境变量 DM_D2R_BINTOOL 指向可执行文件。
- 严格检查原始 pettype.txt 的 hireable.basemax=1 与 single.basemax=1，再只把 hireable.basemax 修改为 2。
- 编译原始完整 Excel 数据生成 pettype.bin，并与用户自己 Switch 3.3 原始游戏文件**逐字节比对**；一旦不一致就停止构建。
- 实验安装包自动启用只读 DM_DUAL_MERC_PROBE=1（覆盖层标志），观察服务器宠物类别 7、客户端佣兵所属 ID、动作模式和状态。
- 绝不触碰原版 .d2s 格式、原 Bundle ID、主分支键鼠适配、正常版本的数据表。

## 真机测试流程

1. 备份角色、佣兵装备与共享仓库，**只使用无贵重装备的新建离线测试角色**。
2. 第一幕雇佣一名不穿装备的罗格，进入游戏，观察日志服务器宠物类型7=1与客户端属主佣兵=1，记录单位 ID。
3. 第二幕再雇佣一名不穿装备的枪兵，观察第一名是否消失或被替换，并记录两侧单位 ID。
4. 切换城镇/传送/小站，检查两人的跟随、攻击和单位状态是否一致。
5. 测试一人死亡后另一人的状态。复活 NPC 是否能分别识别两人仍待验证。
6. 保存退出、重新加载角色，检查佣兵身份与装备。原版存档只包含原生单佣兵语义，因此可能丢失第二人。

日志格式示例（ID / 类号 / 动作模式 / 客户端标记）：

    DM_DUAL_MERC_PROBE：拍 250 玩家 id 1 服务端宠物类型7=1 [123:338:1] 客户端属主佣兵=1 [123:338:1:f0]

只有服务器与客户端同时追踪两个**不同**佣兵 ID，且在地图切换后持续存在、独立攻击时，才能判定运行时双佣兵测试成功。显示两个 ID 本身仍不足以证明。

## 第二阶段

- 若 NPC 雇佣第二人时会销毁第一人：定位并安全拦截原生单佣兵替换流程。
- 若两人共存却只能装备一人：修改目标选择，客户端与服务器均按佣兵 ID 处理，而非选择首个类别 7 单位。
- 若存档只保留一人：保留原版 .d2s 的第一个佣兵，第二人持久化到独立版本化侧文件，并与角色档原子提交；先验证装备唯一 ID、死亡状态与 iCloud 冲突。

此实验仅面向个人离线单人游戏，不面向 Battle.net、局域网或生产存档。

## 第二阶段：双佣兵雇佣决策规则（已提交纯逻辑，尚未接通游戏）

`dm/host/dm_dualmerc_policy.h` 定义服务器必须执行的决策逻辑（无副作用）；`dm/host/tests/test_dualmerc_policy.c` 覆盖空队伍、新增、跨难度同幕、满员选择、死亡佣兵占位、非法状态与取消边界。测试命令：

    cc -std=c11 -Wall -Wextra -Werror -pedantic dm/host/tests/test_dualmerc_policy.c -o /tmp/test_dualmerc_policy && /tmp/test_dualmerc_policy

状态规则：一名第二幕佣兵无论普通/噩梦/地狱，按第二幕同一个名额计算；已死亡但未解雇的佣兵仍占名额。队伍不足两名且所雇佣的幕尚未占用时直接新增；同幕已有佣兵时只能替换该佣兵（先确认）；满两名且新佣兵属于另一幕时必须让玩家明确选择要替换的一个，取消后所有东西保持原样。第四幕原版没有可雇佣的佣兵。

**此头文件目前没有接入原生 NPC 雇佣代码，不会让现有 IPA 自动支持两人。** 客户端提示只能呈现服务器返回的候选方案；真正的检查、创建、替换与装备所有权必须由服务端按同一事务完成。玩家确认时需用最新队伍状态再次计算，避免弹框期间状态变化导致替错。

### 游戏引擎尚缺的四个接口（必须先确认偏移与调用约定）

1. NPC 接受雇佣前：拦截原生“删除旧雇佣→新增雇佣”的单佣兵分支，先读取新佣兵所属幕（Hireling 记录中的 Act，不能按当前难度或城镇猜测），并调用决策规则；选择/取消时原原生事务不能提前释放已有单位。
2. 服务端宠物/佣兵所有权：确认不同单位 ID 能同时存在、独立跟随/死亡/复活；不能靠界面伪造第二名，也不能用只改 `pettype.bin` 代替。
3. 装备面板：按稳定的佣兵槽 ID（0/1）选择目标佣兵，在客户端与服务端都查验物品容器目标；不能继续使用“首个 hireling”指针。替换某一名之前必须安全卸下或保全其装备，绝不直接销毁容器。
4. 原生存档与侧文件：原版 `.d2s` 保留与原版兼容的主佣兵，第二名身份、装备位流、经验与死亡状态放在**同角色目录**、带版本/校验的 `.swmerc`；与 `.d2s` 同一次工作目录原子提交。加载时按稳定角色/槽身份校验，不得用运行时 unit ID 做跨会话外键。旧版程序打开新档时需要防降级保护；未实现和验证前**不得启用第二人装备的正式存档**。

### 真机验收矩阵（尚未通过）

- 第一幕 + 第二幕两名同时出现、移动、攻击，地图/传送/进出游戏保持两名；
- 同幕跨难度只能替换同一名；两名已满时选任一名替换，取消不改变队伍；
- 两名同时装备不同装备，交换/放入储物箱/死亡/复活/退出重进均无复制或丢失；
- 人物存档与侧文件同步提交，存盘失败回滚、iCloud 冲突不静默覆盖装备；
- 开关关闭的普通游戏与原版单佣兵功能完全一致。

上述事项没有完成以前，PR 继续保持 Draft，不合并主分支，不发布为“已实现双佣兵”的安装包。

### 实机雇佣命令追踪补充

实验开关 `DM_DUAL_MERC_PROBE=1` 现在还会在服务端命令分派入口，只读记录 **首字节为 0x36 的候选雇佣命令** 的长度与最多 16 字节原始数据。此操作码来源于旧版协议线索，**未验证等同于 Switch 3.3 的真实雇佣包**；不能凭这一条日志直接修改原生代码。与同一日志中的“服务端宠物类型7=...”和“客户端属主佣兵=...”两侧单位 ID 变化对照，才能确定被替换的先后。若测试时没有 0x36，必须另行采集 `DM_C2S_LOG` 完整包流定位真实命令。当前观测不阻止原版替换。

### 从玩家自有 3.3 NSO 确认原生命令处理入口（只读，新增）

上游已在 `dm/verify/command_packet_format.md` 确认 C2S 表偏移 `main+0x20a4190`。新增独立脚本 `dm/verify/hire_handler.py`，只接受构建号 `db0507f36b84200ac05f75d76ed5026f` 的原始 `main` NSO，并按照 Switch AArch64 RELA 重定位和 ELF unwind 函数起点，报告以下三个命令的*候选*处理函数地址：`0x36`（经典版雇佣）、`0x38`（NPC 动作）、`0x62`（经典版复活）。在 Switch 3.3 上它们的含义仍需实际验证。

    python3 dm/verify/hire_handler.py /path/to/owned/main --out /tmp/merc_hire_handlers.json

输出包含 handler RVA、原始字节前缀与直接 `BL` 调用的候选目标，不包括或上传任何游戏 NSO 字节，不会修补程序。这些候选点与 `DM_DUAL_MERC_PROBE` 的雇佣前后两端佣兵单位日志结合，才能进一步定位真正的原生替换处理函数。脚本无法在无原始游戏 `main` 的公开仓库中完成实机解析，**不表示已拦截或修复替换行为**。

CI 增加纯标准库的 NSO 指针表/重定位/范围防错单测与 Linux C 双佣兵规则单测；CI 不需要 NSO 游戏程序、不可验证真实雇佣。

### 雇佣前后短窗口逐拍采样（只读）

实验模式收到首字节为 `0x36` 的候选包时，在进入原生服务端处理函数**之前**强制记录一次两端佣兵快照，并在其后 100 个服务端拍中逐拍扫描差异；只在数量、ID、模式或属主状态变化时输出，避免固定 25 拍采样漏掉短暂共存。记录中的每个单位增加 `a1/a2/a3/a5` 推测幕别（从类号 271/338/359/560/561 映射，未知 `a0`），同时报告超额两名与同幕重复（560 与 561 同属第五幕）。此映射仅供诊断，真正雇佣要按 `Hireling.txt` 实际候选记录确定。

仍然没有修改任何雇佣、装备或存档行为。若 Switch 3.3 不使用 `0x36`，会缺少加密集采样窗口，需要从完整 `DM_C2S_LOG` 确定正确命令后再改；不能将空日志当作没有雇佣请求。

### 运行时原生函数指针检查（只读，新增）

在带 `dual_merc_probe.enabled` 标志的 iPad 实验包里，进入游戏后会从已经由游戏装载器执行重定位的 `main+0x20a4190` 命令表读取 `0x36`、`0x38`、`0x62` 三个候选包的处理函数指针，要求函数位于已映射可执行正文且四字节对齐，并仅扫描其起始 128 字节内的 ARM64 `BL` 直接调用。日志只打印模块 RVA 和候选调用目标，不打印指针绝对地址、NSO 程序字节或游戏资源，**不会写入客体内存**。这些目标可能跨函数边界或只是旧协议对应的其他函数，不能直接用作有副作用的剪口。需要与前后佣兵单位状态日志核实真实替换发生处，才有条件实施原生双佣兵改写。

### 直接从 Prepared iOS 包解析游戏雇佣命令表（不需要实机启动）

新增 `dm/verify/hire_handler_guest.py`：读取经原游戏程序改写并签名封装的 `source-payload.zip` 中 `Guest.framework/Guest` Mach-O 节（`__dmmainx0` 和 `__DMmainW,__img`），按同包 `main.fixups.tsv` 与 `main.cuts.tsv` 验证平台、游戏构建号及长度，重建只读地址空间前缀；复用 `nsoimg.relocs` 和 `hire_handler.inspect` 抽取服务端候选包 `0x36/0x38/0x62` 的 RVA 和直接调用目标。完整游戏程序的字节不会进入日志或输出 JSON，也不执行/修改代码。

    python3 dm/verify/hire_handler_guest.py /path/to/source-payload.zip --out /tmp/dualmerc-handlers.json

该分析可在私有构建工作流缓存的 Prepared 包上执行；若入口只是一层转发函数，还需进一步检查调用链及真正的佣兵删除和创建函数，禁止直接按候选 RVA 打补丁。
